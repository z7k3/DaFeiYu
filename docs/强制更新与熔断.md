# 强制更新与熔断

4.1.7 起使用 `force_versions` 精确名单。旧 `force` / `force_from` 保留给历史客户端；新客户端只有在清单缺少名单字段时才回退旧协议。

## 字段与判定

| 字段 | 含义 |
| --- | --- |
| `latest` | 旧轨道推荐的安装版本；必须已有对应安装包 |
| `force_versions` | 最多 256 个三段或四段版本号；精确数值匹配，`4.1.6` 等于 `4.1.6.0`，不等于 `4.1.6.1` |
| `force` | 旧协议：true 立即要求更新，false 只提示，null 或缺失使用时间闸 |
| `force_from` | 旧协议在 force=true 时的下界；实际范围是 `[force_from, latest)`，不是“只上一版” |
| `force_after_hours` | 仅在走旧协议且 force=null 时使用，起点为 released_at |
| `kill_below` | 独立熔断线，低于它的旧版得到 Kill；force=false 或空名单不能撤销它 |
| `manifest_version` | 每次修改策略严格递增；回滚内容也要增加，不能退回旧序号 |
| `epoch / brand_latest / target / legacy_latest` | 正式版迁移的代次与双轨目标，保持现有迁移约定 |
| `channel` | 目前预留，不能只靠它隔离旧客户端的候选发布 |

同代客户端按以下顺序判定：

```text
本机版本 >= 目标版本                 → 正常
本机版本 < kill_below                → Kill
force_versions 字段存在：
    命中精确名单                      → Force
    未命中、空名单或名单格式错误       → Warn，到此结束
force_versions 字段缺失：
    force=true 且不低于 force_from    → Force
    force=true 但低于 force_from      → Warn
    force=false                      → Warn
    其他情况                         → 沿用旧时间闸
```

新名单与旧 force 布尔独立。显式 `[]` 不回落旧强制；`null`、字符串、非版本项等错误值也降级为不强制。只有完全删除字段才回退旧协议。跨代时同代名单清空但保留“字段存在”的状态，不能把旧代事故名单或旧布尔强制套到新代。

`kill_below` 是停止使用整个旧版本前缀的工具，不用于单一版本事故；`4.17` 不是 `4.1.7`。运维工具拒绝两段阈值。

## 4.1.6 配置事故与 4.1.7 修复

4.1.6 存在配置覆盖和人设保存问题。4.1.7 包含待发布的配置保护、人设保存修复及迁移能力，不需要再安装版本号更低的 4.1.6.1。

`scripts/release-update-policy.json` 为 4.1.7 指定候选发布策略：

```json
{
  "latest": "4.1.7",
  "force": true,
  "force_from": "4.1.6",
  "force_versions": ["4.1.6"],
  "kill_below": null
}
```

生成器切换到 4.1.7 时才应用该策略。重新生成已刹车的同一版本不会再次开启强制。公开模板在安装包可用之前仍指向已发布版本，保持 force=false、force_versions=[]。

客户端兼容边界：

| 客户端 | 读取行为 |
| --- | --- |
| 4.1.7 起 | 有新名单就完全按名单决定，不会因后续 latest 前进而再次被旧字段强制 |
| 4.1.0～4.1.6 | 不认识名单，按旧 force / force_from；4.1.6 判为 Force，较早版本为 Warn |
| 4.1.0 以下且支持旧 force | 不认识过滤字段，可能一起被判为 Force；不能声称精确覆盖这些版本 |

上述是策略判定，不代表已有客户端一定执行启动阻断。按 v4.1.6 源码，启动走 allowBlocking=false，只显示提示；远端清单不能修补已安装代码。4.1.7 修正启动入口，但不能反向保证所有 4.1.6 自动升级。发布时应同步停止推荐 4.1.6，并通知受影响用户退出旧版、备份、安装修复包。

## 后续发布不误伤已修复版本

发布 4.1.8 时可以保留兼容字段，同时保持事故名单不变：

```json
{
  "latest": "4.1.8",
  "force": true,
  "force_from": "4.1.6",
  "force_versions": ["4.1.6"],
  "kill_below": null
}
```

4.1.7 未命中名单，只提示；4.1.6 继续按旧协议要求升级。后续目标必须保留事故修复，并验证从受影响版本直接升级。保留 force_from 本身不能达到这个效果。

## 候选生成、公开与回滚

1. 在分支完成代码、启动器编译与覆盖升级验证。不要提前让公开清单指向不存在的安装包。
2. tag 工作流调用同一个 make-manifest 生成器，只向 `artifacts/setup/release-manifest.json` 写候选清单。Actions 上传资产包，不创建公开 Release，也不自动提交清单回 main。
3. 维护者核对安装包、SHA256SUMS 与候选清单。验证安装阶段不改配置，首次启动迁移有备份，人设修改经刷新和重启仍保留。
4. 安装包与校验资产公开可用后，再公开候选清单，并通过 PR 同步同一份内容到仓库根文件。不要重新生成另一份不同序号或内容的清单。
5. 若候选生成后在线策略又改变，发布前必须重新核对所有已发出的最大序号，避免用旧候选覆盖后续刹车。
6. 回滚时发布更高序号的刹车清单；停止推荐问题安装包。撤销强制不会自动卸载或降级已经装上的版本，优先前进修复。

本地只准备候选，不修改公开模板：

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File scripts/make-manifest.ps1 -Version 4.1.7 -TemplateFile release-manifest.json -OutFile artifacts/setup/release-manifest.json
```

## 运维命令

```text
node scripts/manifest-policy.js --force-versions 4.1.6,4.1.2  精确指定问题版本
node scripts/manifest-policy.js --force-versions []         新客户端不强制，不回落旧协议
node scripts/manifest-policy.js --force-versions null       删除字段，回退旧协议，慎用
npm run brake                                             同时撤销旧布尔强制和新名单
npm run unbrake                                           显式回退旧时间闸，慎用
npm run force-now                                         显式回退旧布尔强制，慎用
node scripts/manifest-policy.js --kill-below null           独立撤销熔断线
```

`--force` 和 `--force-from` 单独使用只改旧协议；例如 `--force false --force-versions 4.1.6` 可以让支持新协议的受影响版本更新、让旧客户端保持提示。紧急刹车使用 `npm run brake`，不能只把旧 force 改成 false。所有命令支持 `--file` 编辑候选文件，修改后都会递增序号。

## 执行与网络边界

- 启动器在首次检查完成前阻止内核和桥接启动；Force / Kill 在启动和手动检查时真实执行。点击更新横幅也按同一策略处理。
- 运行中每 6 小时静默检查，保持只提示，不自动打断正在进行的会话。
- Force 下载失败仍按既有策略提示后退出；安装脚本失败恢复、独立恢复界面和清单验签仍是后续改进项，不能声称本次已完成。
- 多源及本地缓存取最高序号；缓存保留名单的缺失、空值降级和命中语义。旧在线响应不能覆盖更高序号缓存。
- 没有清单也没有缓存时放行；版本号无法读取时放行。无后端无法保证离线或未重启的用户全部升级。
- 清单尚未验签；序号仲裁减少缓存回退，不等于发布者身份验证。
