# 正式版更新迁移

4.1.6.1 是迁移启动器，`package.json` 使用 `updateEpoch: 1`。正式版使用 `version: "1.0.0"`、`updateEpoch: 2`，显示版本仍取 version，不需要品牌版本映射。

## 清单与发布

准备源码时不要提前把线上清单指向尚不存在的安装包。CI 会把包的 updateEpoch 写入 epoch，并把当前版本写入 brand_latest 和 target；latest 默认等于当前版本，有 legacy_latest 时则保留迁移入口。

发布 4.1.6.1 后，将 CI 生成的清单同步回 main。发布 1.0.0 时保留下面的双轨配置（其余时间、摘要、强制策略字段仍须完整填写）：

```json
{
  "latest": "4.1.6.1",
  "legacy_latest": "4.1.6.1",
  "brand_latest": "1.0.0",
  "epoch": 2,
  "target": "1.0.0",
  "manifest_version": 20
}
```

manifest_version 的 20 仅为示例：实际必须大于所有已经发布的源。epoch 与本地 updateEpoch 先比较：远程更高时允许跨代更新，相等时仅比较 brand_latest，远程更低时忽略。target 必须与 brand_latest 一致，避免展示与安装错配。

- 迁移版与正式版均使用 `v版本号` 标签。新启动器从该标签的 Release 下载安装包与 SHA256SUMS.txt，不依赖哪个 Release 当前被标记 latest。
- 已发布旧客户端仍从 releases/latest/download 下载。因此所有仍需兼容旧用户的 latest Release 都要附带原版 4.1.6.1 安装包，并在 SHA256SUMS.txt 保留对应哈希；旧 Release 不删除。
- 4.1.6.1 必须作为普通 Release 提供给旧客户端，不能只发布预发行版。
- 不要在 1.0.1 时自动移除兼容入口。删除 legacy_latest 并让 latest 变为 1.x 后，尚未迁移的旧客户端会因本地 4.x 数字更大而判定“已是最新”，不再提示，需手动下载安装。
- 旧客户端不支持离散强制名单。此次只实现更新轨道兼容，不开启强制策略。新旧代共用的 force_from / kill_below 不应混写不同代版本阈值；跨代解析会清除这些阈值。
- 插件可用 appCompatibility 同时声明两代范围，不需要拆包；appEpoch 简写仍支持单代。外部市场生成与校验仍需同步，仅正式代可用的包需隔离出旧目录。未声明正式代兼容的旧包需停用检查，详见「插件市场规范.md」。
- 已有 Release 和 tag 保持不动；新代 epoch 不能解决同名 Git tag 冲突，发布前仍须检查目标标签是否已存在。

启动器重新发布不等于已签名；正式签名安装包应由 tag 构建流水线生成并验证。

## 插件市场与本地包双兼容

市场条目和 ZIP 内 plugin.json 使用同一兼容片段（其余必填字段保留）：

```json
{
  "MinAppVersion": "4.1.2",
  "appCompatibility": [
    { "appEpoch": 1, "minAppVersion": "4.1.2" },
    { "appEpoch": 2, "minAppVersion": "1.0.0" }
  ]
}
```

客户端 updateEpoch 决定选择哪项，再检查该项 minAppVersion / maxAppVersion。插件自己的 Version 与客户端版本体系无关，仍按插件原有版本递增。

旧客户端不认识数组，只读顶层 MinAppVersion / MaxAppVersion，因此双兼容包顶层仍写旧代真实范围。缺省新字段的旧包只属于旧代；人设分享导出主动生成双兼容声明。外部市场仓库尚未同步，本次宿主修改不代表远端已接受投稿。
